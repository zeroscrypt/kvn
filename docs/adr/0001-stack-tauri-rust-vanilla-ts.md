# ADR 0001. Стек клиента: Tauri 2 + Rust + vanilla TypeScript

Статус: принято (2026-10).

## Контекст

Нужен максимально эффективный кросс-платформенный клиент (macOS → Linux →
Windows) с терминальным UI, отдельный от готовых GUI-клиентов и без
лишних зависимостей. Кандидаты: Electron, Flutter, Qt/QML, Tauri, Go+Wails.

## Решение

- **Оболочка — Tauri 2.** Использует системный WebView (WKWebView на macOS,
  WebView2 на Windows, WebKitGTK на Linux): итоговый бинарник — единицы
  мегабайт и десятки мегабайт RSS вместо сотен, как у Electron. Rust-ядро
  Tauri даёт честный async-runtime и нормальное управление процессами.
- **Бизнес-логика — Rust-workspace** (`kvn-core`, `kvn-engine`): парсинг
  ссылок, генерация конфига, машина состояний, управление процессом Xray,
  проверки здоровья и статистика. Крейты не зависят от UI и покрыты
  юнит- и интеграционными тестами.
- **Фронтенд — vanilla TypeScript + Vite**, без JS-фреймворка: интерфейс —
  это один экран «терминала» (статус, список профилей, лог). React/Vue
  добавили бы вес и сложность без выгоды для такого UI.

## Последствия

+ Малый размер и потребление памяти; нативный системный WebView.
+ Ядро полностью тестируемо без UI; можно позже сделать CLI поверх тех же
  крейтов.
− UI-часть (TS) покрывается вручную + типами; автотестов на TS нет
  (сознательно: логика вынесена в Rust, а UI-слой тонкий).
− Tauri тянет за собой WebKitGTK на Linux (системная зависимость сборки).

## Альтернативы и почему нет

- **Electron** — сотни МБ на диске и сотни МБ RSS; противоречит цели.
- **Flutter** — свой рендеринг, но тяжёлый рантайм и неудобная работа с
  процессами/PATH-окружением системного уровня.
- **Qt/QML** — долгие лицензионные размышления и не «терминальная»
  эстетика из коробки.
