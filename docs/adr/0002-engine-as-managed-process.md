# ADR 0002. Движок — отдельный управляемый процесс Xray-core

Статус: принято (2026-10).

## Контекст

Варианты интеграции с Xray-core:

1. Встроить ядро как Go-библиотеку (cgo/go mobile) в приложение;
2. Xray-core как внешний процесс, которым мы управляем;
3. Свой туннель (собственная реализация VLESS/REALITY) — исключено как
   «непроверенная криптография».

## Решение

Запускаем **официальный бинарник Xray-core отдельным процессом**, которому
пишем сгенерированный конфиг во временный файл (`runtime/client.json`,
права 0600) и запускаем `xray run -config …`.

Ключевые правила:

- **Конфиг проверяется самим движком** (`xray run -test`) до запуска туннеля:
  ошибки генератора не доходят до пользователя «наполовину рабочим»
  соединением.
- **Готовность = реальный трафик.** После `wait_for_port` (порт слушает)
  выполняется сквозной HTTP-запрос *через туннель* (SOCKS5 CONNECT на
  generate_204-цели). Только после этого состояние переходит в `Connected`.
- **Останавливаем строго.** SIGTERM с grace-периодом, затем убийство;
  процесс запускается в отдельной сессии (setsid), и при выходе приложения
  мы гарантированно гасим его (watchdog + shutdown-хук).
- **Статистика — через собственный stats API движка**
  (`xray api statsquery`), без встраивания gRPC-стека.

## Последствия

+ Используется та же версия ядра, что у пользователя на сервере (Xray);
  поведение предсказуемо и обновляется независимо от приложения.
+ Полный контроль жизненного цикла процесса; статистику и логи можно
  показывать как есть.
+ Нулевой риск для криптографии: всё делает официальный Xray.
− Нужно управлять бинарником движка (см. ADR 0003).
− Две сущности (app + engine) надо синхронизировать при завершении —
  решено watchdog-процессом и хуком выхода.

## Проверено

Интеграционные тесты `crates/kvn-engine/tests/xray_integration.rs`
запускают реальные серверный и клиентский Xray на 127.0.0.1 и прогоняют
живой трафик через туннели VLESS TCP / WS / XHTTP (REALITY), проверяя
также ненулевые счётчики статистики и корректную остановку процесса.
