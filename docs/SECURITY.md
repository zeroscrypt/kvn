# Безопасность KVN

Документ описывает модель угроз, что именно сделано для защиты и где
проходят границы гарантий. Принцип: лучше честно назвать ограничение, чем
обещать несуществующее.

## Модель угроз

Кого/что защищаем:

- **Секреты пользователя**: UUID/passwords из share-ссылок, URL подписок
  (часто содержат токен), сгенерированный конфиг — от утечки в логи,
  диагностические файлы и на диск в читаемом для других виде.
- **Целостность движка**: подмена Xray-бинарника или архива при скачивании.
- **Пользователя от чужого контроля**: приложение принципиально не просит
  пароль администратора панели 3x-ui и не делает запросов к панели; входные
  данные — только share-ссылки/подписки.

Вне зоны гарантий (честно):

- Скомпрометированная локальная машина (кейлоггер, root) — не защищаемся.
- Сам VPN-сервер и его оператор.
- Содержимое, которое отдаёт подписка: тело подписки парсится строго, но
  «какие ссылки сервер вернул» — ответственность сервера.
- Локальные процессы того же пользователя могут подключаться к SOCKS/HTTP
  портам на 127.0.0.1 — это нормальное свойство локального прокси
  (Loopback-only; доступ извне невозможен).

## Секреты: пути и защита

- Все значения-секреты в Rust обёрнуты в `kvn_core::Secret`: `Debug` и
  `Display` печатают `***`, реальный доступ — только явный `.expose()`.
  Это делает случайную утечку через `{:?}`/`{}` невозможной.
- Редакция ссылок (`redact_link`, `redact_url`) режет UUID, пароли и
  токены прежде, чем строка попадёт в журнал. Ошибки парсеров никогда не
  содержат значения полей — только имена.
- `state.json` пишется атомарно (tmp+rename) с правами `0600`; временный
  файл создаётся сразу с `0600`, чтобы окна «файл создан, права ещё нет»
  не существовало.
- Сгенерированный конфиг движка (`runtime/client.json`) — тоже `0600`.
- **Диагностический экспорт не содержит секретов**: профили описываются
  именем, id, сводкой и endpoint-ом; подписки — редакцией URL; настройки —
  без полей пути движка (сам путь не секрет, но и он не обязателен).
  Экспорт — осознанное действие пользователя (кнопка/команда).
- Журнал в UI может содержать только то, что прошло редакцию; тест
  `secret`-крейта фиксирует инвариант «ошибки не содержат креденшелов».

## Движок: цепочка поставки

- Релизные сборки несут движок **в комплекте** (sidecar, ADR 0005);
  приложение также умеет скачать архив Xray только из официального
  GitHub-релиза (`XTLS/Xray-core`, зафиксированная версия) и **до
  распаковки** сверяет SHA-256 архива с пином в `core/xray.json`
  (манифест встраивается в бинарь на этапе компиляции; скрипты и CI
  читают тот же файл). Подмена релиза/MITM не проходит.
- Из архива извлекается ровно один файл `xray`; записи с путями,
  содержащими `..` или абсолютные компоненты, отклоняются (zip-slip).
  Распаковка — во временный файл + atomic rename.
- Любой бинарник (включая «свой» из настроек) обязан пройти пробу
  `xray version` — иначе он не будет запущен. Произвольный файл с диска
  невозможно «скормить» пайплайну как движок.
- Процесс движка запускается **без shell**: `Command::new(binary).args([…])`
  с фиксированным набором аргументов (`run -config <path>`), поэтому
  argument injection исключён. Путь к конфигу и логам строится только из
  наших каталогов.
- Пользовательский путь движка в настройках — ответственность
  пользователя; UI честно пишет об этом. Рекомендуется официальный.

## Цепочка поставки самого KVN

- Релизные артефакты собираются в GitHub Actions из тега; к каждому
  артефакту прикладываются build-provenance аттестация
  (`actions/attest-build-provenance`) и `SHA256SUMS`; черновик релиза
  публикуется без пересборки — опубликованные байты тождественны
  отревьюенным.
- Все GitHub Actions пришпилены к полным commit-SHA; зависимости
  обновляет Dependabot, уязвимости Rust-крейтов проверяет cargo-deny на
  каждый PR, JS-зависимости — `pnpm audit` в CI; параллельно работают
  CodeQL и OpenSSF Scorecard.
- macOS-сборки не подписаны (нет Apple Developer account) — это честно
  указано в README и релизных заметках; целостность проверяется через
  `SHA256SUMS` и аттестацию происхождения сборки.

## Криптография

- Своей криптографии нет вообще: TLS 1.3, REALITY, VLESS/VMess/Trojan/SS
  выполняет Xray-core — проверенный, широко используемый движок.
- Клиент **не отключает проверку сертификата сам**: если в share-ссылке
  пришёл `allowInsecure=1`/`insecure=1`, параметр сохраняется как есть, но
  профиль помечается предупреждением «TLS verification disabled», и
  предупреждение показывается в UI (сайдбар и карточка профиля).
  Приложение никогда не добавляет его от себя.
- Выбор `verifyPeerCertInNames`/fingerprint-ов и прочие тонкости REALITY —
  в терминах Xray; мы прокидываем параметры ссылки 1:1 и не «улучшаем» их.

## Сетевой периметр

- Inbound-порты (SOCKS/HTTP) слушают **только 127.0.0.1**. Наружу ничего
  не открывается.
- Stats API Xray — только loopback и случайный порт, живущий в пределах
  запущенного процесса.
- Health-check — настоящий трафик через туннель к `generate_204`-целям
  (Google/Cloudflare/…) по plain HTTP: это осознанный компромисс, чтобы не
  зависеть от TLS-перехвата; в запросе нет ничего, кроме пути и хоста.
- «Ping» профиля — прямой TCP-connect с машины пользователя (проверяет
  доступность сервера вне туннеля; это явно отдельная кнопка, не путается
  с проверкой туннеля).
- Системный прокси включается только пока туннель в состоянии
  `Connected` и только по явному действию (кнопка) либо по включённой
  пользователем настройке «Set system proxy automatically while
  connected».
- **Нет телеметрии.** Сетевые запросы приложения: скачивание движка (по
  кнопке), обновление подписок (по явному вводу/кнопке), health-check
  через туннель, ping по кнопке. Больше ничего.

## Системный прокси

- Мы **сохраняем прежние значения** (сервис, включность, адрес, порт) до
  изменения и восстанавливаем их при отключении.
- Пока прокси «наш», на диске лежит `sysproxy-backup.json`. Если
  приложение упало, при следующем старте прокси восстанавливается из
  бэкапа (иначе система осталась бы указывать на мёртвый порт).
- Права root не нужны и не запрашиваются.
- Windows: не реализовано (явная ошибка команды), см.
  `docs/PLATFORM_SUPPORT.md`.

## UI-слой

- Content Security Policy окна ограничена: только свои ресурсы, IPC и
  локальный dev-сервер; никакого удалённого кода.
- Никакого интернета внутри WebView: все сетевые действия идут через
  Rust-команды.
- Импорт из файла читается JS `FileReader` из локального файла,
  выбранного пользователем в системном диалоге; содержимое уходит в Rust
  как текст и парсится строго типизированными парсерами.
- Capability окна — только `core:default` (событийная шина и плагины не
  используются вообще).

## Известные ограничения

- Тела подписок читаются целиком в память (лимит `ureq` по умолчанию);
  гигантские «подписки» (десятки МБ) могут занять память — считается
  маловероятным для реальных 3x-ui, но отмечено.
- `state.json` зашифрованным не является (это позволило бы только
  усложнить модель без реального выигрыша при живом пользователе рядом);
  защита — права `0600` и отсутствие альтернативных копий.
- Engine-бинарь, установленный KVN, не подписан нами — но и не наш: это
  официальный релиз, проверенный по digest-у; то же верно для движка в
  комплекте (sidecar): байты — из официального архива, digest — из пина.
- Кнопка «Проверить обновления» ядра обращается к `api.github.com`
  (чтение тега последнего релиза Xray-core; никакие данные о пользователе
  не отправляются, в логах — только результат).
