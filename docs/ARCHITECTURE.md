# Архитектура KVN

## Обзор

KVN — тонкая десктопная оболочка вокруг управляемого процесса Xray-core.
Вся предметная логика (парсинг, генерация конфига, машина состояний)
вынесена в два Rust-крейта без зависимостей от UI и платформы:

```
┌──────────────────────────────────────────────────────────────────┐
│ apps/desktop  — Tauri 2 приложение                               │
│                                                                  │
│  frontend (vanilla TS + Vite)                                    │
│    main.ts     — состояние UI, полинг, горячие клавиши           │
│    views.ts    — рендер (сайдбар, статус, события, статусбар)     │
│    modals.ts   — импорт/подписки/настройки/движок                 │
│    palette.ts  — командная палитра (⌘K)                          │
│         │ invoke("get_status" | "connect" | …)                   │
│  ├──────┴────────────────────────────────────────────────┐       │
│  │ src-tauri: commands.rs (API), controller.rs (движок   │       │
│  │ состояния), tray.rs (меню-бар), store.rs (persist),   │       │
│  │ sysproxy.rs, engine_install.rs, eventlog.rs, paths.rs │       │
│  └──────┬────────────────────────────────────────────────┘       │
└─────────┼────────────────────────────────────────────────────────┘
          │
   ┌──────┴─────────────┐        ┌─────────────────────────┐
   │ crates/kvn-core    │        │ crates/kvn-engine       │
   │  uri/     парсеры  │        │  process.rs  spawn/stop │
   │  xray/    конфиг   │        │  health.rs   «живой»    │
   │  state.rs маш. сост│        │              трафик     │
   │  secret.rs секреты │        │  stats.rs    счётчики   │
   └────────────────────┘        │  manifest.rs пин движка │
                                 │  install.rs  sha256     │
                                 │  version.rs  probe      │
                                 └───────────┬─────────────┘
                                             │ spawn/kill, api
                                  ┌──────────┴──────────┐
                                  │  Xray-core процесс  │
                                  │  runtime/client.json│
                                  │  SOCKS/HTTP inbound │
                                  └─────────────────────┘
```

## Поток подключения (по шагам)

1. Пользователь нажимает **Connect** (или Enter на профиле, или из
   палитры). Команда `connect` валидирует id профиля, сохраняет его как
   активный в `state.json` и отправляет в контроллер событие
   `ConnectRequested`.
2. Контроллер (единственный владелец состояния) прогоняет событие через
   `kvn_core::state::StateMachine` и получает список действий.
3. Действие `SpawnEngine` порождает задачу:
   - находит движок: пользовательский путь → установленный KVN → `PATH`,
     каждый кандидат обязан пройти `xray version`;
   - выбирает свободный loopback-порт для stats API;
   - собирает клиентский конфиг (`build_client_config`) с inbound-ами
     SOCKS/HTTP на 127.0.0.1, stats API на loopback и всеми параметрами
     профиля; замечания генератора (`notes`) улетают в журнал;
   - пишет конфиг **атомарно** в `runtime/client.json` (права `0600`);
   - проверяет конфиг самим движком: `xray run -test -config …`;
   - запускает процесс (`spawn_engine`, отдельная сессия, логи в файлы);
   - ждёт готовности порта (`wait_for_port`, до 8 с) — при неудаче убивает
     процесс и отдаёт ошибку с хвостом логов движка.
4. `EngineReady` → машина состояний переводит соединение в фазу
   **checking** и запускает `RunHealthCheck`: SOCKS5 CONNECT + HTTP-запрос
   к `generate_204`-цели **через туннель**. Латентность измеряется в момент
   прихода заголовка ответа, дренаж ограничен (64 КБ / 1.5 с).
5. `HealthCheckPassed` → состояние **Connected** (только теперь!). Запущен
   поллер статистики (раз в секунду, `xray api statsquery`).
6. UI всё это время опрашивает `get_status` (каждые ~700 мс) и
   `get_events` (каждые ~900 мс) и рисует фазы, метрики и лог.

## Машина состояний и устойчивость

Состояния: `Disconnected`, `Connecting{attempt, engine_ready}`,
`Connected`, `Reconnecting{attempt}`, `Stopping{pending_profile}`, `Error`.

Правила:

- **Готовность двигателя не равна готовности туннеля.** `Connected`
  достижимо только после `HealthCheckPassed`.
- **Ретраи ограничены**: экспоненциальный бэкофф (1 с → 2 → 4 …, кап 30 с,
  максимум 5 попыток), затем `Error` с исходной причиной.
- **Неретрайбельные ошибки** (неверный конфиг, нет движка, ошибка
  аутентификации) не ретраятся вовсе.
- **Epoch-защита**: каждое асинхронное событие (spawn, health, retry)
  помечается номером эпохи; при отмене/переключении/стопе эпоха
  инкрементится, и «хвосты» старых задач молча отбрасываются. Медленный
  spawn не может воскресить отменённое соединение: перед сохранением
  процесса задача сверяет эпоху и при расхождении убивает свежий процесс.
- **Watchdog** каждые 500 мс проверяет `try_wait` процесса движка и при
  неожиданном выходе посылает `EngineExited` (факт, не гонка поколений) —
  машина состояний переводит это в реконнект или ошибку.
- **Выход приложения**: `RunEvent::ExitRequested` → `StopRequested`, до 2 с
  ожидания `Disconnected`, затем принудительное убийство процесса и
  восстановление системного прокси.

## Статистика трафика

- Источник — собственный stats API Xray (`xray api statsquery` через
  локальный loopback-порт со случайным номером; порт живёт только пока
  процесс запущен).
- Считаем **inbound-счётчики** (`socks-in`, `http-in`) и исключаем
  `api`-inbound (иначе служебные запросы попадают в статистику).
- Эмпирически проверено (см. `docs/RESEARCH.md`): для VLESS исходящий
  uplink-счётчик outbound-а не инкрементируется движком — поэтому
  inbound-счётчики первичны, outbound-профиль используется как фолбэк.
- Значение счётчика приходит то числом, то строкой, а при нуле поле
  `value` вообще отсутствует — парсер обрабатывает все три случая.

## Хранение данных

Всё лежит в каталоге приложения (macOS:
`~/Library/Application Support/dev.zeroscrypt.kvn`):

| Файл | Назначение | Права |
|---|---|---|
| `state.json` | профили, подписки, настройки | `0600`, атомарная замена (tmp+rename) |
| `bin/xray` | установленный движок | исполняемый |
| `runtime/client.json` | сгенерированный конфиг | `0600` |
| `logs/kvn.log` (+`.log.1`) | журнал событий приложения (для пост-мортема) | обычные |
| `logs/engine.log`, `logs/engine-stderr.log` | логи движка | обычные |
| `logs/diagnostics-*.txt` | экспорт диагностики (без секретов) | `0600` |
| `sysproxy-backup.json` | прежние настройки системного прокси | `0600` |

Повреждённый `state.json` не удаляется: он переименовывается в
`state.json.bad-<ts>`, и приложение стартует с дефолтами.

## API приложения (Tauri commands)

`get_status`, `list_profiles`, `import_from_text`, `delete_profile`,
`rename_profile`, `set_active_profile`, `connect`, `disconnect`,
`ping_profile`, `get_events`, `clear_events`, `subscription_list`,
`subscription_add`, `subscription_update`, `subscription_delete`,
`settings_get`, `settings_set`, `engine_status`, `engine_install`,
`engine_set_path`, `system_proxy_set`, `diagnostics_export`.

UI **не** получает push-события: полинг двух дешёвых команд даёт простую,
предсказуемую модель синхронизации (и не требует permissions на событийную
шину в capability).

## Тестовая стратегия

| Слой | Чем проверен |
|---|---|
| Парсеры, `Secret`, машина состояний, генератор конфига | 62 юнит-теста `kvn-core` |
| Процесс движка, health, stats, install | 14 юнит-тестов `kvn-engine` |
| Сквозной путь с **живым Xray**: VLESS TCP / WS / XHTTP+REALITY, реальный трафик, ненулевые счётчики, корректный стоп | 4 интеграционных теста `kvn-engine` (`XRAY_BIN=… cargo test -p kvn-engine`) |
| Персистентность, парсинг networksetup, хвосты логов, журнал | 16 тестов `kvn-desktop` |
| UI | ручной прогон + строгая типизация TS (`tsc --noEmit` в сборке) |
